## 1. 病根（审查实测，Node 桌面口径；移动端约 ×2–4）

1. **P0-1 记账链**：`readDone` 逐词 `push2` → 每词一次全量 `replay` + 整库 `stringify` +
   同步 `setItem`。6000 条日志单次 replay 10.5ms + stringify 3.3ms（0.9MB）→ 一句 3 词 ≈ 41ms；
   20000 条 ≈ 96ms。日志只增不减，越用越卡。
2. **P0-2 滚动链**：scroll 监听里 `paint()` 同步直调（无合并）；paint 内部无条件重写
   `btnPlay.innerHTML`、全量扫 seek 刻度（最多 ~400 个）、任务模式两遍 `updateMarkers`、
   `positionListenMini` 布局读 —— 每滚一下全付。
3. **P1-3 滑块**：拖动每跨一档（input）立刻 `etaFor` → 一个 0.3–0.9s 的全量 `estimateDays`
   （实测 672ms）；5→240 最多 47 档排队，主线程啃成幻灯片。
4. **P1-4 clampGloss**：逐段「归零(写) → 量(读) → 写回」交织 → 每段一次强制回流；
   全库 308 段 × 每段 8 个注音的规模。
5. **P2**：`cmpIndex` 每次 render 全库重扫（1833 句正则 + 3245 词条 + 220 卡）；
   `_inTextSet` 每次 render 置 null → 开词库必全量重扫 `.w`；`todayOfArticle` 每次调用
   前后双清 `_cachedPlan`（首页 6 张卡 = 6 次全量装配）；单词本「加载更多」整页重渲（O(n²)）。

## 4. 回归锁（`playwright-tests/journeys/app3/perf-guards.spec.ts`，3 条）

1. **记账句级批量**：`Storage.prototype.setItem` 计数钩子精确圈住一次 `TASK.readDone(0)`
   （3 词句）—— 写次数 = 1、事件 delta = 3（行为等价也在锁里，防「为了少写而漏账」）。
2. **滚动不重绘**：录音笔桩（`window.speak` 攒回调不兑现）稳定 playing 态 →
   MutationObserver 盯 `#btnPlay` → 两次 `scrollTo` 后计数必须 0。
3. **工期预览合并**：一次 evaluate 连发 5 个 input（20→40）→ 500ms 后 `etaCalls` delta = 1；
   读数跟手、change 前不落账、change 后落账。

## 5. 评估后不动的（明确保留，不是漏项）

- **cloudPull 全量分页拉取**：按 `ts` 排序的全量合并是跨设备协议的一部分；设备时钟偏移下
  增量游标会**静默漏事件**（数据完整性 > 流量）；事件量级（两年 ~2 万条 <10MB、分页 1000/页）
  可接受。要动它得连协议一起重设计。
- **backdrop-filter 滚动降级**：玻璃质感是全局设计语言（几十处 + 主题锁），降级牵动主题系统
  与动效，收益不确定；等低端机实测反馈再单独立项。
- **初始渲染懒加载（只渲目标篇）**：`.w` / `.sent` 全库 DOM 是词库（📖 标记）、正文定位、
  任务标记（updateMarkers/artOfSent）的共享输入，改动面过大；只省一次性 ~几十 ms，
  风险/收益不匹配。
- **offscreen 段落不测**：跳过会让「滚入视口但没触发重夹」的段落露出破绽（夹紧没有 scroll
  触发路径），保持全库测（两阶段后成本已可控）。
- `sw.js` 导航重写缓存：异步、影响有限（审查已判可接受）。
