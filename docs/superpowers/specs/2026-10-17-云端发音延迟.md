# 云端发音延迟（2026-10-17）

## 报障

用户：「句子的发音加载很慢，点击单个单词的发音更慢，需要等更久。这个加载慢的问题，你有什么好的方案解决吗？」

## 先说清「慢」在哪

云端合成是**一句一请求**：`POST functions/v1/tts {text, voice, rate}` → 服务端调 Azure → 返回整段 mp3 →
客户端 `await r.blob()` → `URL.createObjectURL` → `<audio>.play()`。

一次往返的耗时几乎全是**固定开销**：

| 段 | 量级 | 能不能省 |
|---|---|---|
| 取 session（`auth.getSession()`，偶发刷新令牌） | 10~300ms | 能（缓存 token） |
| 边缘函数接单 / 冷启 | 200ms~1.5s | 服务端 |
| Azure 神经语音合成启动 + 整句合成 | 300ms~2s | 服务端 |
| 音频下载（词条 3~8KB / 句子 40~120KB） | 50~300ms | 词条几乎为 0 |

所以**单词不会比句子快**：它省掉的只是最后那 3~8KB 的下载，前三段一分不少。
这也是「点单词更慢」的观感来源 —— 等 2 秒只为听 0.4 秒的一个词，心理落差最大。

结论：客户端唯一能大幅改善的办法不是「优化下载」，而是**在用户点之前就把这段合成做完**
（预取），外加**别自己把已经发出的请求掐掉**。

## 查出来的四处「自己坑自己」

### ① 同一句连点两下 = 从头再来

点词卡会走 `openPop()`，里面**立刻自动读一遍**（`speakAside(el.dataset.disp)`）；
手快再点词卡上的「发音」时，第一次的合成还在飞。旧 `CLOUD.play()` 第一件事是 `this.stop(clipKey)`，
而 `stop` **无条件** `this._playCtl.abort()` —— 正在飞的那份被自己掐掉，第二次只能从零合成一遍。
更糟的是 `_pend` 里还挂着被判死的 promise，`synth` 会直接把这条拒绝复用出去 → 走 `degrade`
「云端音色这一句没放出来，本句改用本地音色」。

**修法**：`synth` 登记 `_playCtlKey`；`stop(keepKey)` 发现「正在合成的就是马上要播的这句」就不 abort，
交给 `_pend` 复用。两下点击共用同一份请求。

### ② 词条与句子共用一个 120 条 FIFO 缓存池

`_cacheSet` 只有一档上限 120，且淘汰的是 Map 里**最早插入**的那条（FIFO）。词条 3~8KB、
句子 40~120KB 混在一个池里，读长文时 `launch` 每句扔 8 个预取进去，刚点过的词条很快被挤出去，
下次再点又是冷启动。

**修法**：按缓存键第 4 段的词数分池（≤2 个词 = 词条），词池 400 条（≈2~3MB）、句池 100 条；
命中时 `_touch` 把该条移到队尾 —— 才是真 LRU。正在播放的那条永不回收（原有保护保留）。

### ③ 入口预热从「下一句」起，当前句永远冷

`warmupCloudAhead()` 原本 `from = idx + 1`，只热后面 8 句。而按 ▶ / 点句最先要的正是**当前句**。

**修法**：`from = idx`（无续读位时仍从 0 起），预热「当前句 + 后 7 句」。
另外补两处触发面：
- `render()` 末尾调 `warmResume()`（**自由阅读也预热**，不只是任务模式），带 120s 同篇去重；
  开屏时 `CLOUD._on` 还没回来就 3s 后补一次；
- 指针在某句上停 800ms 就单独预热这一句（桌面端点句播放基本不用等），800ms 节流防扫读泛洪。

### ④ 点句播放把刚发出的预热掐成 stale

`playFrom()` 起播前会 `CLOUD.stop()`（清旧队列）。不带 key 时，**刚由预热发出、还在飞的那份**
会被 abort 成 `stale`，随后 `synth` 重开一份 —— 预热的钱白花，要等的时间照旧。
悬停预热 → 立刻点句这个组合必中。

**修法**：`playFrom` 把这一句的 `clipKey` 交给 `stop(keepKey)`。
顺带把缓存键收成唯一出处 `CLOUD.clipKey(text, voice, rate)`（原先 `play` 与 `synth` 各写一遍、
靠注释「必须逐字一致」硬撑），`text` 统一 `trim` —— 预热取原始句、播放取 DOM 文本，两边必须同键。

## 没做的（可选下一步）

- **单词音频静态化**：语料共 6118 个不同词形（`sections.json` 全量统计），按 24kbps 单声道约
  30MB / 1.2 万个文件（英/美两套）。能换来「首次点击 <100ms」，但要么进 git（仓库暴涨）、
  要么进 Supabase Storage（要一次性批量合成 + 上传）。目前靠「点过一次就永久进 IndexedDB」自愈。
- **服务端缓存**：`functions/v1/tts` 按 `(voice, rate, text)` 缓存到 Storage，第二次起直接回放。
  源码不在本仓库，需要单独改。
- **token 内存缓存**：`_fetchTTS` 每次 `await this.session()`。量级只有几十毫秒，先不动。

## 锁

`playwright-tests/journeys/app3/tts-latency.spec.ts`（5 条，均已反向验证：把修法还原 → 对应一条必红）

1. `clipKey` 的 rate 段按**合成档**记：0.1/0.8/1 共用 `1.00`、1.2/1.25 共用 `1.25`、2/3/5 共用 `1.50`；
   前后空格归一（预热取原始句、播放取 DOM 文本，必须同键）；
2. 同一句连点两下只合成一次、不 abort、不降级、音频真挂上 `<audio>`；
3. 30 个词条 + 150 个句子后词条一条不少、句池仍 ≤100；
4. `warmupCloudAhead()` 在 `idx=2` 时包含第 2 句（不只 3）；
5. 预热 600ms 在飞时点播同一句：不 abort、只合成一次、音频播出去。

> 与倍速线的交界：`clipKey` 与 `cloudSynthRate` / `playRate` 是同一条链，rate 段永远由
> `cloudSynthRate` 归一。第 1 条就是为此设的护栏 —— 自定义 0.1~5.0 落在这三档附近时，
> 不会因为换了个档位就多合成一份。合并倍速改动后务必把 `rate-cloud.spec.ts` 一起跑。
