# 设计：走完全部词要多久（第三期·进度与预估）

日期：2026-09-21　状态：**待他复核**（口径已定，未开工）
需求原话：「我设定计划和执行计划我都需要明确的指导我完成这些所有单词，需要多久。可能会完成多个这样的轮次。」

## 0. 一句话

在**设定计划**和**执行计划**两处，都告诉他同一件事：按现在这个每天分钟数，把整本词表全部学到"毕业"要多少天；并把他这两周的真实节奏当第二个数并排放，供对照。

## 1. 他已经拍掉的三条口径（本轮设计的前提，不再讨论）

1. **完成 = 按词毕业数**，不是按句遍历数。分母是词表里全部词头。
2. **界面不提"轮"**。旧表回炉只说成"今天有 K 个词到期回炉"。
3. **设定屏是只读实时预估**：拖分钟数 → 那行字跟着变。不做"填考试日反推分钟数"（那是被否掉的第三个选项）。

**一处更正**：我先前在对话里说词表是 3222 个词 —— 那是旧数。实测 `shadow/data/vocab.json` 与 `data/vocab.json` 都是 **3245** 个词头，两站键集相等（门禁 3 第 4 条保证）。**界面上这个数一律实时取 `shadow/data/vocab.json` 的键数，不写死** —— 它每加一张卡就会变（本文里出现的 3245 都只是今天的实值举例）。

## 2. 为什么现在答不出这个问题（实测现状）

- 「今天 N 个」的分母是**句**：`plannedToday()` 把「当天已读句数 + 队列里未读句数」钉成一个数，显示成 `① 通读 done/planned`。词只在注脚里以"覆盖 M 个词"出现一次。
- 全表完成百分比**不存在**。代码里唯一和"走完"有关的东西是 `planCapacity / fmtCycles / planSummary / adjustPlan` 一组旧计算器 —— 实测各只有 2 处引用（定义 + 导出），**没有任何界面入口**，是死代码。而且它算的是"句子轮次"，不含词毕业，直接接回界面会答非所问。
- 「轮」这个概念是第一期**主动删掉的**，不是没做：`docs/PRD.md:562`「『X 轮』『已读 x/1833』已删除，不再有"读完一轮"这种全局承诺」；`docs/2026-09-20-学习计划与任务模式重设计-PRD.md:502` 留了口子：「若他坚持保留『XX 天读完一篇』的仪式感，第三期用『已毕业句数 / 1833』这一个数承担，且只能出现在栏 2」。本设计是那个口子的**兑现 + 修订**：口径从"句"换成"词"，位置从"只许栏 2"放宽到他要求的两处（见 §6）。

## 3. 支撑设计的实测事实

| 事实 | 数值 | 来源 |
|---|---|---|
| 词表规模 | 3245 词头 | 两站 vocab.json 实数 |
| 课文规模 | 1833 句 / 308 段 | sections.json |
| 每句挂的目标词 | 平均 2.22 个（4072 次标记，**全部有卡、无一遗漏**；3245 个词头全部在课文里被标出过） | 标记解析 |
| 毕业判据 | `reps ≥ 20` 且 `ok3 ≥ 1`（③ 选义至少对一次） | `plan-engine.js` `MASTER_REPS` / `stageOf` |
| 毕业后回访 | 每 **14 天**一次，**永远** | `wordInterval`：`reps ≥ 20` 恒返回 `GRADUATED_INTERVALS[0]`；**`[1]=30` 那档取不到，是死值** |
| 每日装队列的唯一输入 | 分钟数（5–180）；一句代价 = 句时 + 2×每题（`secNew` 25s、`secReview` 8s、`secQuiz` 6s，可被 `rate` 缩放） | `assemble` |

**前向模拟结果（空状态冷启动、日界凌晨 4 点、③ 正确率 85%，跑真引擎 `assemble` + 事件流）**

| 每天分钟 | 走完 3245 个词 |
|---|---|
| 15 | 887 天 |
| 30 | 446 天 |
| 60 | 227 天 |
| 90 | 153 天 |

三条从表里读出来的结论，界面必须承认：

1. **近似反比**：分钟翻倍≈天数减半 —— 因为瓶颈是"每天能产生多少次接触"（3245×20 ≈ 6.5 万次接触），不是别的。
2. **不是一行线性公式能骗过去的**：模拟里第 3 天起"今天新词"经常为 0（到期复习优先吃预算），新词是**脉冲式**挤进来的。所以"今天新词 N 个"会在 0 与几十之间跳，预估必须看累计，不能拿当天数外推。
3. **算得起**：Node 里跑完 887 个模拟日 ≈ 0.7 秒（0.8ms/天）。浏览器同一段代码同量级 → **松手才算、结果按天缓存**的话，界面完全扛得住。

## 4. 设计

### 4.1 数据层：一个函数，复用引擎，禁止第二套算式

`estimateDays(state, minutes, opts)` → `{days, doneBy, graduatedNow, total, capped}`

- 内部就是本次探针的做法：拿当前 `state` → 逐日 `assemble(state, …)` → 把当天队列翻成 contact/quiz 事件 → **只把新事件**喂进 `replay(…, {state})` → 数毕业词，直到全毕业或到上限。
- **必须复用 `ShadowPlan.assemble` / `mkContact` / `mkQuiz` / `replay`**，不许写"词数×20÷每天句数"这类旁路公式。理由是本仓库反复栽在同一处：一份逻辑两份实现就会漂移（宽度尺、标记拆分、表头规则、落地器都是这样修的）。
- 需要的唯一引擎改动：`replay(events, opts)` 现在恒从 `emptyState()` 重建，续算要 `opts.state`（探针里是打字符串补丁做的）。正式改法：`const st = o.state || emptyState();`，默认行为不变。
- 上限 `maxDays`（默认 1095 天 / 3 年）；跑满仍未毕业 → `capped: true`。
- 正确率假设（默认 0.85）写进函数参数，且**在界面上以一句话交代**，不许假装它是实测。

### 4.2 显示层：三处，同一个数

| 位置 | 文案（界面原话） |
|---|---|
| 初次设置（拖分钟那行下面） | `这样选：走完全部 3245 个词约 887 天` |
| 计划页改分钟 | 同一行，随分钟实时重算；封顶时改说 `按每天 15 分钟，三年内到不了终点` |
| 今天面板注脚（栏 2） | `已毕业 480 / 3245 · 走完约 887 天 · 今天 8 个词到期回炉` |

- **两个数并存但名字必须不同**：`走完约 N 天`（模型外推）与 `你最近 14 天实际势头约 M 天`（实测均速）。第一期"计划 1.4 轮 / 已完成 2 轮"打架的教训不是"只能留一个数"，而是**两个数不许共用一个名字**。
- 「实际势头」只在有 ≥14 天记录时出现，否则整行不显示（不显示 ≠ 显示 0）。
- 三处出现的是**同一个函数返回值**，不许各自算一遍、各自格式化。
- 界面文本里禁止出现"轮"字（写成验收项，见 §7）。

### 4.3 交互与性能

- 滑块 **拖动过程中不重算**，松手才算（模拟 0.5–1 秒，逐帧跑会卡）。
- 结果按 `(毕业基线日, 分钟数, 词表版本)` 缓存，同一天同一分钟数不重复跑；期间那行显示 `算一下…`。
- 他做了一天真实任务后缓存自动失效（基线日变了），第二天打开重算。

## 5. 边界与失败处理

- **没有 state / 全新用户**：空状态照样能算（模拟表就是空状态），所以第一天就有数 —— 这正是"用模拟而不是历史均速"的理由。
- **`pausedNew`（暂停新词）开着**：模拟必须走同一开关，否则给出的天数偏乐观。
- **多设备**：模拟跑在本机 state 上；两设备记录不同步时数字不同。完成记录已是只追加事件流上云，读回后两边一致，本设计不新增同步面。
- **词表变动**（加卡、以后补词）：分母与天数都会跳，属正确行为；界面写"全部 X 个词"实时值，别写死。
- **`capped: true`**：只说"三年内到不了终点"，**不许**显示"1095+ 天"这种假精确。

## 7. 测试

**单元（`plan-engine` 第一次有正经测试，顺带解掉整改清单那条 P0「计划引擎 0 测试」）**

1. 单调性：`minutes` 增大 → `days` 严格不增。
2. 冷启动：空 state 也返回有限天数，不抛错。
3. **只喂新事件 ≡ 全量重放**：同一事件流，增量续算与从空重建，最终 `graduated` 计数必须逐词相等（这条守住 §4.1 那个 `opts.state` 改动）。
4. 预算不破：每个模拟日 `stats.usedSec ≤ budgetSec`（引擎构造保证，写成断言防回归）。
5. `capped` 分支：`maxDays=30` 时不得返回 `done:true`。
6. 分母不写死：把词表数注成任意值，界面串必须跟着变。

7. 设置屏拖分钟 → 那行"走完约 N 天"的数字变化且与 `estimateDays` 一致。

## 8. 明确不做（YAGNI）

- 不做目标日反推、不做"每天该几分钟"的建议值（他已选只读预估）。
- 不做"第 N 轮"、不做轮次记账。
- 不做曲线图/日历热力图。
- **不改 14 天回访档位**：`GRADUATED_INTERVALS[1]=30` 那个死值是排程问题，改了会把所有人的到期分布重排，与本需求无关，另案处理（但它会让"走完"比理论值更慢，所以 §3 的模拟已经把它算进去了）。

## 9. 等他答的三条（不影响我先写实现计划的骨架）

1. **887 天这种数字要不要就这么摆着？** 另一种表达是"到 12 月 20 日能毕业 1900 个词"（同一函数换个问法）。要不要顺手也显示后者？
